# Raw provenance schemas

Authority: the implementation plan, Sections 7.1 (version axes), 7.4
(identifier and collision rules), and 7.5 (object keys and the canonical
field sets); requirements STO-002, STO-010, STO-011, STO-013, SID-005,
SID-006; and threat PI-07 (fabricated provenance in the canonical
occurrence manifest). The schemas are
[`schemas/v1/occurrence-manifest.json`](../../schemas/v1/occurrence-manifest.json)
and
[`schemas/v1/upload-attestation.json`](../../schemas/v1/upload-attestation.json);
they share the v1 wire vocabulary pinned in
[`schemas/v1/common.json`](../../schemas/v1/common.json) and produce
identities with the constructions pinned in
[`schemas/v1/ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json).

## The two records and what stays out

Raw provenance is split by *what the record is about*, not by where it is
sent. The occurrence manifest is **source-stable provenance**: every field
is an input to, or a deterministic derivation of, the session, artifact,
and occurrence identities, so its canonical bytes are identical no matter
who uploads, when, or how often (STO-010). The upload attestation is
**uploader and request provenance**: who presented which frozen request
for which occurrence (STO-013). Identity is separate by construction —
`occurrence_id` folds in session/artifact/generation/range/digest,
`attestation_id` folds in occurrence plus uploader plus frozen request —
so an origin and an authorized relay converge on one occurrence while
recording distinct, separately auditable attestations (EC-05A), and a
relay can never overwrite source provenance (SID-006).

Each envelope field lands in exactly one durable home, or deliberately
nowhere:

| Envelope field | Occurrence manifest | Upload attestation |
|---|---|---|
| `tenant_id`, `origin_client_id` | yes | yes |
| `harness`, `upstream_session_id`, `id_source` | yes | — |
| `artifact_kind`, `adapter_id`, `adapter_projection_version`, `adapter_artifact_id`, `generation`, `range_kind`, `range_start`, `range_end` | yes | — |
| `blob_digest`, `storage_profile` | yes | — |
| `session_hash`, `artifact_hash`, `occurrence_id` | yes (self-verifying) | `occurrence_id` only |
| `source_time` | yes (when the source has one) | — |
| `uploader_client_id`, `request_id`, `attestation_id` | — | yes (self-verifying) |
| `capture_time`, `envelope_creation_time`, `delegation` | — | yes |
| `transport_encoding`, `incoming_checksum(_algorithm)`, `compressed_size`, `uncompressed_size` | — | — |

Wire-only rows are deliberate: transport checksums and sizes describe one
delivery attempt, not the source or the frozen request, and the envelope
is not a stored object — the server derives every durable key from
validated fields. Per-attempt authorization (epoch, key, timestamp), the
per-attempt signature, and the server commit time exist only in the signed
receipt (plan Section 7.5); both schemas reject those names outright, the
way the envelope schema does, so per-attempt material can never make
byte-identical retries impossible.

The manifest is **self-verifying**: `session_hash`, `artifact_hash`, and
`occurrence_id` are each re-derivable from the manifest's own fields, and
`attestation_id` from the attestation's own fields — an auditor needs
nothing but the stored object (STO-011). The stored blob's uncompressed
size is recoverable from its `zstd-v1` frame header, so no size field is
duplicated. The manifest carries the full artifact-identity tuple
(`artifact_kind`, `adapter_id`, `adapter_projection_version`,
`adapter_artifact_id`) even though only the hashes strictly identify it,
because the envelope is not durable: without the tuple, the artifact's
identity would survive only as an unrecoverable hash input and catalogs
could not be rebuilt from the raw namespaces (STO-011).

## Versioning

`occurrence_version` and `attestation_version` are independent axes (plan
Section 7.1): readers retain old-version support; within a major, new
optional fields are additive and old readers retain them inside signed
bytes; new required fields, redefined fields, a changed canonical field
set, or changed identity rules require a new major, and unknown majors and
unknown security- or identity-bearing enum values fail closed. Every
`x-archivist.bearing` marks which enum is which; `delegation` is the one
enum this family adds and it is security-bearing.

## The example bundle

[`schemas/v1/examples/provenance/`](../../schemas/v1/examples/provenance/)
is generated by [`tools/provenancegen.py`](../../tools/provenancegen.py)
with zero entropy: every identifier, timestamp, and payload byte is a
pinned synthetic constant (SEC-010), and every derived value — the two
hashes, the digests, both occurrence IDs, all four attestation IDs, and
all three kinds of object key — is computed with the byte-exact
construction of `ingest-identifiers.json`, so the bundle doubles as a
golden-vector table. The manifest records the scenarios and their
assertions:

1. **direct-upload** — one occurrence, one direct attestation; the
   manifest validates while naming no uploader, request, transport,
   per-attempt, or server field.
2. **delegated-relay** — the *same* occurrence manifest bytes, plus a
   second attestation with `delegation=relay` and a different uploader;
   identity differs by `uploader_client_id` alone.
3. **identical-bytes-distinct-occurrences** — a second origin/session pair
   (different harness, adapter-minted `id_source=synthetic` session ID)
   submits the same canonical payload: the archive holds exactly one blob
   object key and two distinct occurrences, each with its own
   attestation (STO-002).
4. **multiple-attestations-one-occurrence** — three attestations name one
   occurrence: the origin's, the relay's, and the origin's re-frozen
   request after the spool entry was lost, which differs only in
   `request_id` (hence `attestation_id`) and its own capture/envelope
   times; a retry of any *one* frozen request rewrites its identical
   object rather than adding a fourth (STO-004, STO-013).

Regeneration and verification:

```sh
tools/provenancegen.py --generate   # rewrite the bundle (byte-identical)
tools/provenancegen.py --verify     # byte-compare, schema-validate, check invariants
```

`--verify` regenerates the bundle and byte-compares every file, requires
each JSON file to be exactly its canonical rendering plus one trailing
LF, validates every instance against its schema (draft 2020-12, with
`common` resolved from `schemas/v1/common.json`), checks each expected
object key against the key patterns `common.json` pins, and re-checks the
delegation and cross-reference invariants. Exit codes: 0 pass, 2 drift or
non-canonical formatting, 3 schema or invariant failure, 4 `jsonschema`
unavailable.

## Relationship to the ingest wire family

This family shares `schemas/v1/common.json` with the ingest wire schemas
(envelope, request, identifiers, errors): one vocabulary per version
directory, no per-family copies of the identifier grammars or key
patterns. The derived-identity constructions live in
`ingest-identifiers.json` and are normative for both families — the same
`occurrence_id` names the wire envelope's claim and the stored manifest's
key.

## Open questions

- The v1 canonical field sets are exactly the plan's (Section 7.5). The
  envelope's optional correlation identifiers (`parent_session_id`,
  `orchestrator_attempt_id`, `trace_id`, `inference_request_id`) are
  wire-only today and therefore not durable; if Phase 9 correlation needs
  them in the archive, they arrive as additive optional fields (or a v2),
  decided with the normative protocol contract rather than smuggled in
  here.
- `uncompressed_size` and an event-count twin are the likeliest additive
  optional manifest fields if catalogs turn out to need them without a
  blob read; they are source-stable, so they do not violate STO-010 —
  they are simply not pinned yet.
