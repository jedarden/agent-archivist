# Agent Archivist protocol contract (v1)

Normative for the `v1` wire protocol: the `POST /v1/ingest` request framing,
per-attempt authorization, canonical forms, the ingest envelope, and the
version axes beneath them. Every rule in this document carries the identifier
of the locked requirement, threat, plan section, or error-registry entry it
renders normative.

Authority and precedence, strongest first:

1. [Requirements](../notes/requirements.md) — the locked requirement IDs
   (`VAL-*`, `ID-*`, `SID-*`, `STO-*`, `SEC-*`, `ERR-*`) cited inline.
2. [`schemas/v1/`](../../schemas/v1/) — the machine-readable shapes, with the
   [language-neutral conformance corpus](../../schemas/v1/examples/conformance/)
   as their executable ground truth. Where this document appears to disagree
   with a schema pattern, bound, enum, or golden vector, the schema or vector
   is authoritative and this document must be corrected.
3. This document — the human-normative prose binding 1 and 2 together.
4. [Implementation plan](../plan/plan.md) Sections 7.1–7.3 — the design record
   this section renders normative; where plan and requirements disagree, the
   requirements win (plan Section 1).

Error codes, HTTP statuses, and retryability named below are registered in
[`tools/error-codes.toml`](../../tools/error-codes.toml); the error body they
travel in is the closed six-field `archivist.error/v1` shape
([`schemas/v1/ingest-error.json`](../../schemas/v1/ingest-error.json)) — every
framing-time failure returns that body with a stable machine-readable code and
echoes no transcript content (VAL-007).

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as
described in RFC 2119, bounded by the cited requirement.

## 1. Request framing and canonicalization

### 1.1 Version axes and fail-closed behavior

The protocol versions these dimensions independently (plan Section 7.1;
VAL-001):

| Dimension | Initial form | Compatibility rule |
|---|---|---|
| HTTP route | `/v1/ingest` | Breaking wire changes use a new route major |
| Envelope schema | `envelope_version` | Unknown major fails closed |
| Occurrence schema | `occurrence_version` | Readers retain old-version support |
| Upload-attestation schema | `attestation_version` | Readers retain old-version support |
| Storage layout | `v1` key prefix | Never silently repurpose an existing prefix |
| Adapter projection | adapter + projection version | Preserve the version in provenance |
| Derived pipeline | pipeline name + version | Rebuildable; never overwrites raw data |

Rules:

- **VAL-001** — the request and every envelope carry explicit protocol and
  schema versions. The v1 envelope pins `protocol_version` and
  `envelope_version` to the integer `1` (`const` in
  [`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)); an unknown
  major on either axis is rejected fail-closed with
  `envelope.version_unsupported` (HTTP 400) before any payload processing —
  never a best-effort parse.
- **Framing-layer version check (VAL-001)** — the media type of request part
  one is `application/vnd.agent-archivist.envelope+json;version=1`; the
  `version` parameter tracks `envelope_version`. A v2 envelope is framed as
  `version=2`, and an old server rejects it at the framing layer, before
  parsing the body, with `envelope.media_type_unsupported` (HTTP 415).
- **Unknown security- or identity-bearing enum values fail closed (VAL-001)**
  — in this section's scope: `artifact_kind`, `range_kind`, `id_source`,
  `storage_profile`, `transport_encoding`, `incoming_checksum_algorithm`
  (`checksum-algorithm`), and `signature_algorithm`. Each is a closed v1 enum
  in [`common.json`](../../schemas/v1/common.json) carrying
  `x-archivist.bearing` with `failClosed: true`; any other value is
  `envelope.schema_invalid` (HTTP 400, VAL-002). Corpus proof:
  `invalid-unknown-enum-value`.
- **Additive evolution within a major (plan Section 7.1)** — inside `v1`, new
  *optional* envelope fields are additive: old readers retain them inside
  signed bytes and ignore their semantics (`unknownFields: retain-ignore`).
  New required fields, redefined fields, or changed identity rules require a
  new major. The old-reader/new-writer and new-reader/old-writer fixtures of
  plan Section 7.1 enforce this.
- **No floating-point values (plan Sections 7.1 and 7.3)** — protocol
  structures contain no floats anywhere; every numeric shape is the `u63`
  integer (Section 1.4). A float in an integer field is
  `envelope.schema_invalid` (VAL-002).
- **Package version is not a data-format version (plan Section 7.1)** —
  software semver never substitutes for any axis above.

### 1.2 The multipart request layout

`POST /v1/ingest` carries exactly one occurrence as a `multipart/related`
request body of exactly two parts, in this order (plan Section 7.2):

| Part | Media type | Content |
|---|---|---|
| 1 | `application/vnd.agent-archivist.envelope+json;version=1` | the canonical envelope (Section 1.4), at most 65,536 canonical bytes |
| 2 | `application/octet-stream` (transport `identity`) or `application/zstd` (transport `zstd`) | the payload in the encoding the envelope's `transport_encoding` declares |

Rules:

- The request Content-Type is `multipart/related` with a `boundary`
  parameter. The complete header value — including the boundary — is covered
  by the per-attempt signature (Section 1.3) and MUST match
  `^multipart/related; boundary=[0-9A-Za-z'()+_,.:=?-]{1,70}$`
  (`content_type` in
  [`ingest-request.json`](../../schemas/v1/ingest-request.json); at most 100
  characters).
- The payload part streams; it is never base64-embedded in JSON (plan Section
  7.2). The server SHOULD use bounded-memory streaming and abort uncommitted
  parts on failure (VAL-008).
- A request whose part count or part order differs from the table is a
  framing failure. Part two's media type is pinned by the envelope's
  `transport_encoding` (`partTwoMediaTypeByTransport` in
  [`ingest-request.json`](../../schemas/v1/ingest-request.json)); a
  transmitted part-two media type that does not match the declaration is
  rejected `envelope.media_type_unsupported` (HTTP 415). Any post-signing
  framing alteration additionally fails the covered `content_type` or
  `request_content_digest` (Section 1.3).
- The byte-level reference framing — `--<boundary>` CRLF, one lowercase
  `content-type` header per part, CRLF, part bytes, CRLF, closing
  `--<boundary>--` CRLF — is pinned by the conformance corpus
  (`manifest.json` → `conventions.multipart_framing`) so any implementation
  can rebuild the golden bodies byte-identically. Because the signature
  covers the whole body (below), any post-signing alteration of the boundary,
  the parts, or any payload byte — by the client or on the path — is
  detected: corpus proofs `invalid-altered-framing-boundary` and
  `invalid-altered-payload-byte`, both rejected 401 (ID-007; threat IA-02,
  altered request under a valid signer).
- The server MAY pre-authorize the presenting key ID before the body arrives
  (plan Section 7.2), but commits nothing until the complete signature and
  payload verify (Section 1.3; VAL-004 is the payload-side half).

### 1.3 Per-attempt signature parameters

Every attempt — first transmission or retry — is individually authorized by
an Ed25519 HTTP message signature (plan Section 7.2; ID-004). The signed
values form a closed twelve-field record,
[`schemas/v1/ingest-request.json`](../../schemas/v1/ingest-request.json)
(`additionalProperties: false` — per-attempt state, never retained signed
material, so there is nothing to carry forward and an open shape would only
widen the disclosure surface; ERR-003, ERR-033):

| Field | Shape (exact) | Role |
|---|---|---|
| `http_method` | `const "POST"` | covered method (fail-closed) |
| `route` | `const "/v1/ingest"` | covered route; an unknown route value fails closed exactly as an unknown major does (Section 1.1) |
| `content_type` | string, `^multipart/related; boundary=[0-9A-Za-z'()+_,.:=?-]{1,70}$`, ≤ 100 chars | the complete request Content-Type, boundary included |
| `request_content_digest` | `sha256-hex` | SHA-256 over the whole multipart body as transmitted |
| `envelope_digest` | `sha256-hex` | SHA-256 over the canonical envelope bytes of part one |
| `payload_canonical_digest` | `sha256-hex` | MUST equal the envelope's `blob_digest` (STO-001) |
| `payload_transport_digest` | `sha256-hex` | MUST equal the envelope's `incoming_checksum` (PI-02) |
| `uploader_key_id` | `key-id` (SHA-256 of the encoded public key, `sha256-hex`) | the linked uploader key this attempt authorizes under |
| `authorization_epoch` | integer, 1 … 2⁶³−1 | epoch of the uploader key; rotations and revocations bump it (ID-006) |
| `authorization_timestamp` | `rfc3339-utc-timestamp` | fresh UTC timestamp bound into this attempt |
| `signature_algorithm` | `ed25519` (closed enum) | pinned; not itself covered — the linked-key record and the closed v1 enum carry it |
| `signature` | `ed25519-signature-hex` (128 lowercase hex) | the signature value; not covered |

Rules:

- **Construction (plan Section 7.2)** — the signature is Ed25519 over the
  `ingest-attempt-v1` domain label followed by one `0x00` byte, then each
  covered field as an 8-byte unsigned big-endian length plus exactly that
  many field bytes, in the pinned order
  `http_method, route, content_type, request_content_digest,
  envelope_digest, payload_canonical_digest, payload_transport_digest,
  uploader_key_id, authorization_epoch, authorization_timestamp`, with kinds
  `text, text, text, digest, digest, digest, digest, digest, u63, text`
  ([`ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json);
  golden vectors in the conformance corpus `signing.attempt_input_hex`).
- **Freshness (plan Sections 5 and 7.2; ID-007)** — the authorization window
  is 300 seconds with at most 300 seconds of clock-skew allowance (pinned as
  `authorizationWindowSeconds` / `clockSkewAllowanceSeconds` and
  cross-registered in
  [`control-envelope.json`](../../schemas/v1/control-envelope.json)). A stale
  or altered proof is rejected `auth.authorization_rejected` (HTTP 401);
  corpus proof `invalid-stale-authorization`. A stale epoch is rejected the
  same way (ID-006, ID-007).
- **Retry semantics (plan Section 7.2; ID-007, STO-004)** — none of these
  values enter the envelope. A retry after the window re-authorizes: fresh
  `authorization_timestamp` and fresh signature over the *identical* frozen
  envelope and body bytes, so occurrence and attestation identity are
  unchanged and the commit converges on the same objects. Corpus proof
  `valid-retry-after-window` (epoch 1 → 2, `already_present` × 3).
- **Authorization scope (ID-005)** — the uploader MUST be authorized for the
  declared tenant and origin client; otherwise `auth.forbidden` (HTTP 403).
  Corpus proof `invalid-cross-tenant-forbidden`. A revoked key is
  `auth.revoked` (HTTP 401, ID-006).
- **Substitution (IA-02)** — because method, route, content type, the whole
  body, the canonical envelope, and both payload digests are covered,
  transplanting a valid authorization onto altered content fails the
  signature or the digest equalities above.

### 1.4 Canonical envelope form

The envelope part is JSON in the protocol's canonical form (plan Sections
7.2–7.3):

- **Canonicalization is RFC 8785** over the protocol's value domain: ASCII
  member names, integers, strings, arrays, booleans, and `null` — no floats
  (plan Section 7.1; the `u63` discipline below). String escaping uses the
  short forms plus literal UTF-8; member order is insignificant in
  transmission.
- **Size bound (VAL-002 adjacent cap, plan Section 7.2)** — at most 65,536
  *canonical* bytes (`canonicalMaxBytes` in
  [`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)). Exceeding
  it is `envelope.size_exceeded` (HTTP 400), distinct from any payload limit.
- **Identity binds the canonical form** — `envelope_digest` is computed over
  the RFC 8785 canonicalization of the envelope, not over the transmitted
  bytes; derived identifiers likewise hash each input by its canonical wire
  text ([`ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json);
  Section 2). A transmitted part one that is reordered or differently
  whitespace is valid provided it canonicalizes: corpus proof
  `valid-reordered-envelope-framing` (identities unchanged) and
  `canonicalization.json` case `reordered-whitespace-equivalence`.
- **Malformed for the protocol (VAL-002)** — values with no RFC 8785
  canonicalization are rejected `envelope.malformed` (HTTP 400): duplicate
  member names (parsers disagree on the value) and lone surrogates (no valid
  UTF-8). A float in an integer field canonicalizes but fails the schema:
  `envelope.schema_invalid` (HTTP 400). Corpus proofs in
  `canonicalization.json` → `rejections`.
- **No normalization of identifiers (plan Section 7.4)** — opaque UTF-8
  identifiers are never case-folded, Unicode-normalized, or trimmed; NFC and
  NFD lookalikes are distinct sessions with distinct digests
  (`canonicalization.json` case `nfc-nfd-lookalikes`).

### 1.5 Envelope fields: canonical and excluded

The version 1 envelope (plan Section 7.3;
[`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)) defines 28
required and 5 optional fields. Shared shapes, byte-for-byte from
[`common.json`](../../schemas/v1/common.json):

| Shape | Bound |
|---|---|
| `uuid-v4` | `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, ≤ 36 chars, lowercase canonical text |
| `uuid-v7` | `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, ≤ 36 chars, lowercase canonical text |
| `sha256-hex` | `^[0-9a-f]{64}$`, ≤ 64 chars, lowercase |
| `short-token` | `^[a-z0-9][a-z0-9._-]{0,63}$`, ≤ 64 chars |
| `version-token` | `^[0-9A-Za-z._+-]{1,32}$`, ≤ 32 chars |
| `opaque-id` | UTF-8, 1–1024 **bytes** (`byteMaxLength` is normative; the codepoint `maxLength` of 1024 is its superset) |
| `rfc3339-utc-timestamp` | `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}(\.[0-9]{1,9})?Z$`, ≤ 35 chars |
| `u63` | integer, 0 … 2⁶³−1 |

Required fields, grouped by role (each is `required` in the schema; all
bounds above are exact):

| Field | Shape | Role and citation |
|---|---|---|
| `protocol_version` | `const 1` | route family major; fail-closed (VAL-001) |
| `envelope_version` | `const 1` | envelope schema major; fail-closed (VAL-001) |
| `tenant_id` | `uuid-v4` | issuer-created tenant (plan 7.4) |
| `origin_client_id` | `uuid-v4` | installation that captured the source; scopes the session namespace (SID-001, SID-002) |
| `uploader_client_id` | `uuid-v4` | installation presenting this request; MAY differ from origin under relay (ID-005) |
| `harness` | `short-token` | harness identifier (plan 7.4) |
| `upstream_session_id` | `opaque-id` | the harness's own session ID, or the adapter-minted stand-in when `id_source` is `synthetic` |
| `id_source` | `upstream` \| `synthetic` | origin of the session identifier; a synthetic ID is never inferred from a path name (plan 7.4) |
| `artifact_kind` | `file-slice` \| `database-projection` | kind of source artifact (SID-004); identity-bearing |
| `adapter_id` | `short-token` | projecting adapter; input to the artifact hash (plan 7.4) |
| `adapter_projection_version` | `version-token` | projection version, preserved in provenance (plan 7.1) |
| `adapter_artifact_id` | `opaque-id` | the adapter's opaque artifact identifier (plan 7.4) |
| `generation` | `uuid-v7` | source generation of this snapshot; replacement or incompatible rewrite starts a fresh one (SID-003) |
| `range_kind` | `byte` \| `event` | coordinate kind of the range (SID-004); identity-bearing |
| `range_start` | `u63` | inclusive start coordinate; `range_start ≤ range_end` is server-side (VAL-002) |
| `range_end` | `u63` | inclusive end coordinate; ranges sit inside occurrence identity (SID-005, PI-05) |
| `blob_digest` | `sha256-hex` | SHA-256 of the canonical uncompressed payload — the one digest that names a blob (STO-001); recomputed while streaming (VAL-004) |
| `incoming_checksum` | `sha256-hex` | checksum of the payload as transported; secondary integrity, never content identity (PI-02) |
| `incoming_checksum_algorithm` | `sha256` | closed enum (fail-closed) |
| `storage_profile` | `zstd-v1` | named canonical storage encoder the server must produce (plan 7.6); closed enum (fail-closed) |
| `transport_encoding` | `identity` \| `zstd` | wire encoding of part two; the server decodes exactly one declared encoding — a misdeclaration makes the canonical bytes diverge and the request fails (PI-01) |
| `compressed_size` | `u63` | size as transported; equals `uncompressed_size` under `identity` |
| `uncompressed_size` | `u63` | size of the canonical uncompressed payload; enforced against the decoder's output (VAL-003, PI-03) |
| `capture_time` | `rfc3339-utc-timestamp` | UTC time the client captured this chunk (plan 7.3); uploader-asserted (PI-07) |
| `envelope_creation_time` | `rfc3339-utc-timestamp` | UTC time the client froze this envelope; frozen with the spool entry and reused verbatim on every retry (plan 7.3) |
| `occurrence_id` | `sha256-hex` | deterministic occurrence identity; the server re-derives and refuses a mismatch (SID-005) |
| `attestation_id` | `sha256-hex` | deterministic upload-attestation identity (STO-013) |
| `request_id` | `uuid-v7` | frozen request identifier, generated at spool creation, reused across retries, bound into envelope, attestation, receipt, and error bodies (ERR-025); a correlation handle, not a security identity |

Optional fields (absent, never `null`, when not applicable; additive within
v1 per Section 1.1):

| Field | Shape | Role |
|---|---|---|
| `source_time` | `rfc3339-utc-timestamp` | UTC timestamp embedded in or derived from the source, when one exists (plan 7.5); uploader-asserted (PI-07) |
| `parent_session_id` | `opaque-id` | upstream parent-session correlation, same harness (plan 7.3); never an identity input |
| `orchestrator_attempt_id` | `opaque-id` | orchestrator attempt correlation; joined exactly, never inferred (EC-13) |
| `trace_id` | `opaque-id` | provider trace correlation (CAP-008) |
| `inference_request_id` | `opaque-id` | inference-request correlation (Phase 9) |

**Excluded fields.** The envelope is frozen per request and MUST NOT contain
server commit time, per-attempt authorization material, the per-attempt
signature, or any server attempt correlation (plan Section 7.3). The schema
enforces this by rejecting these six names outright (`not` block in
[`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)):
`authorization_epoch`, `authorization_key_id`,
`authorization_timestamp`, `commit_time`, `correlation_id`, `signature` —
`envelope.schema_invalid` (HTTP 400, VAL-002); corpus proof
`invalid-reserved-field`. That exclusion is precisely what makes the retry
contract of Section 1.3 work: fresh authorization never changes occurrence or
attestation identity. Per-attempt and server material lives in the
signature-parameter record (Section 1.3) and the signed receipt (Section 5),
nowhere else.

Unknown fields with other names are retained inside the signed envelope
bytes and their semantics ignored (Section 1.1; plan Section 7.1).

**Cross-field consistency (VAL-002).** The schema pins syntax and bounds;
the server additionally validates, before committing an occurrence:
`range_start ≤ range_end` and range consistency with the declared sizes;
`compressed_size = uncompressed_size` when `transport_encoding` is
`identity`; calendar validity and bounds of every timestamp; the digest
equalities of Section 1.3; and re-derivation of `occurrence_id` and
`attestation_id` (corpus proof `invalid-occurrence-id-mismatch`). Declared
sizes are evidence, not authority — they are checked against the bytes the
decoder actually produces (VAL-003; Section 3 carries the payload-side
rules).

**Timestamps (plan Section 7.3).** Persisted timestamps are RFC 3339 UTC
(`Z` suffix only, at most nine fractional digits — the
`rfc3339-utc-timestamp` shape); local time is a display choice only.
Durations and retry budgets use a monotonic clock and never appear on the
wire as timestamps.

### 1.6 How this section is verified

- [`tools/check-wire-schemas.py`](../../tools/check-wire-schemas.py) (fast
  lane of [`scripts/definition-of-done.sh`](../../scripts/definition-of-done.sh))
  proves the schema family's coherence: `const` pins on both version fields,

  and `$ref` resolution across the URN space.

  truth of every rule marked "corpus proof" above: golden attempts and
  signatures, canonicalization vectors (including the reorder-equivalence and
  NFC/NFD cases), altered-framing and altered-payload rejections, the
  retry-after-window identity equality, and the reserved-field and
  unknown-enum rejections — regenerated and verified by
  `tools/conformancegen.py --verify` in the same fast lane.
- The old-reader/new-writer and new-reader/old-writer compatibility fixtures
  for the additive-evolution rule (plan Section 7.1) are separately tracked
  work under the umbrella bead.
