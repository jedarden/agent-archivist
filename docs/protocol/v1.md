# Agent Archivist protocol contract (v1)

Normative for the `v1` wire protocol: the `POST /v1/ingest` request framing,
per-attempt authorization, canonical forms, the ingest envelope, the version
axes beneath them, the derived identities and tenant-scoped object layout
those forms name, and the canonical payload and `zstd-v1` storage profile
persisted beneath them. Every rule in this document carries the identifier
of the locked requirement, threat, plan section, or error-registry entry it
renders normative.

Authority and precedence, strongest first:

1. [Requirements](../notes/requirements.md) — the locked requirement IDs
   (`VAL-*`, `ID-*`, `SID-*`, `STO-*`, `SEC-*`, `ERR-*`) cited inline.
2. [`schemas/v1/`](../../schemas/v1/) — the machine-readable shapes, with the
   [language-neutral conformance corpus](../../schemas/v1/examples/conformance/)
   as their executable ground truth. Where this document appears to disagree
   with a schema pattern, bound, enum, or golden vector, the schema or vector
   is authoritative and this document must be corrected.
3. This document — the human-normative prose binding 1 and 2 together.
4. [Implementation plan](../plan/plan.md) Sections 7.1–7.6 — the design record
   this document renders normative; where plan and requirements disagree, the
   requirements win (plan Section 1).

Error codes, HTTP statuses, and retryability named below are registered in
[`tools/error-codes.toml`](../../tools/error-codes.toml); the error body they
travel in is the closed six-field `archivist.error/v1` shape
([`schemas/v1/ingest-error.json`](../../schemas/v1/ingest-error.json)) — every
framing-time failure returns that body with a stable machine-readable code and
echoes no transcript content (VAL-007).

The key words MUST, MUST NOT, SHOULD, and MAY are to be interpreted as
described in RFC 2119, bounded by the cited requirement.

## 1. Request framing and canonicalization

### 1.1 Version axes and fail-closed behavior

The protocol versions these dimensions independently (plan Section 7.1;
VAL-001):

| Dimension | Initial form | Compatibility rule |
|---|---|---|
| HTTP route | `/v1/ingest` | Breaking wire changes use a new route major |
| Envelope schema | `envelope_version` | Unknown major fails closed |
| Occurrence schema | `occurrence_version` | Readers retain old-version support |
| Upload-attestation schema | `attestation_version` | Readers retain old-version support |
| Storage layout | `v1` key prefix | Never silently repurpose an existing prefix |
| Adapter projection | adapter + projection version | Preserve the version in provenance |
| Derived pipeline | pipeline name + version | Rebuildable; never overwrites raw data |

Rules:

- **VAL-001** — the request and every envelope carry explicit protocol and
  schema versions. The v1 envelope pins `protocol_version` and
  `envelope_version` to the integer `1` (`const` in
  [`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)); an unknown
  major on either axis is rejected fail-closed with
  `envelope.version_unsupported` (HTTP 400) before any payload processing —
  never a best-effort parse.
- **Framing-layer version check (VAL-001)** — the media type of request part
  one is `application/vnd.agent-archivist.envelope+json;version=1`; the
  `version` parameter tracks `envelope_version`. A v2 envelope is framed as
  `version=2`, and an old server rejects it at the framing layer, before
  parsing the body, with `envelope.media_type_unsupported` (HTTP 415).
- **Unknown security- or identity-bearing enum values fail closed (VAL-001)**
  — in this section's scope: `artifact_kind`, `range_kind`, `id_source`,
  `storage_profile`, `transport_encoding`, `incoming_checksum_algorithm`
  (`checksum-algorithm`), and `signature_algorithm`. Each is a closed v1 enum
  in [`common.json`](../../schemas/v1/common.json) carrying
  `x-archivist.bearing` with `failClosed: true`; any other value is
  `envelope.schema_invalid` (HTTP 400, VAL-002). Corpus proof:
  `invalid-unknown-enum-value`.
- **Additive evolution within a major (plan Section 7.1)** — inside `v1`, new
  *optional* envelope fields are additive: old readers retain them inside
  signed bytes and ignore their semantics (`unknownFields: retain-ignore`).
  New required fields, redefined fields, or changed identity rules require a
  new major. The old-reader/new-writer and new-reader/old-writer fixtures of
  plan Section 7.1 enforce this.
- **No floating-point values (plan Sections 7.1 and 7.3)** — protocol
  structures contain no floats anywhere; every numeric shape is the `u63`
  integer (Section 1.4). A float in an integer field is
  `envelope.schema_invalid` (VAL-002).
- **Package version is not a data-format version (plan Section 7.1)** —
  software semver never substitutes for any axis above.

### 1.2 The multipart request layout

`POST /v1/ingest` carries exactly one occurrence as a `multipart/related`
request body of exactly two parts, in this order (plan Section 7.2):

| Part | Media type | Content |
|---|---|---|
| 1 | `application/vnd.agent-archivist.envelope+json;version=1` | the canonical envelope (Section 1.4), at most 65,536 canonical bytes |
| 2 | `application/octet-stream` (transport `identity`) or `application/zstd` (transport `zstd`) | the payload in the encoding the envelope's `transport_encoding` declares |

Rules:

- The request Content-Type is `multipart/related` with a `boundary`
  parameter. The complete header value — including the boundary — is covered
  by the per-attempt signature (Section 1.3) and MUST match
  `^multipart/related; boundary=[0-9A-Za-z'()+_,.:=?-]{1,70}$`
  (`content_type` in
  [`ingest-request.json`](../../schemas/v1/ingest-request.json); at most 100
  characters).
- The payload part streams; it is never base64-embedded in JSON (plan Section
  7.2). The server SHOULD use bounded-memory streaming and abort uncommitted
  parts on failure (VAL-008).
- A request whose part count or part order differs from the table is a
  framing failure. Part two's media type is pinned by the envelope's
  `transport_encoding` (`partTwoMediaTypeByTransport` in
  [`ingest-request.json`](../../schemas/v1/ingest-request.json)); a
  transmitted part-two media type that does not match the declaration is
  rejected `envelope.media_type_unsupported` (HTTP 415). Any post-signing
  framing alteration additionally fails the covered `content_type` or
  `request_content_digest` (Section 1.3).
- The byte-level reference framing — `--<boundary>` CRLF, one lowercase
  `content-type` header per part, CRLF, part bytes, CRLF, closing
  `--<boundary>--` CRLF — is pinned by the conformance corpus
  (`manifest.json` → `conventions.multipart_framing`) so any implementation
  can rebuild the golden bodies byte-identically. Because the signature
  covers the whole body (below), any post-signing alteration of the boundary,
  the parts, or any payload byte — by the client or on the path — is
  detected: corpus proofs `invalid-altered-framing-boundary` and
  `invalid-altered-payload-byte`, both rejected 401 (ID-007; threat IA-02,
  altered request under a valid signer).
- The server MAY pre-authorize the presenting key ID before the body arrives
  (plan Section 7.2), but commits nothing until the complete signature and
  payload verify (Section 1.3; VAL-004 is the payload-side half).

### 1.3 Per-attempt signature parameters

Every attempt — first transmission or retry — is individually authorized by
an Ed25519 HTTP message signature (plan Section 7.2; ID-004). The signed
values form a closed twelve-field record,
[`schemas/v1/ingest-request.json`](../../schemas/v1/ingest-request.json)
(`additionalProperties: false` — per-attempt state, never retained signed
material, so there is nothing to carry forward and an open shape would only
widen the disclosure surface; ERR-003, ERR-033):

| Field | Shape (exact) | Role |
|---|---|---|
| `http_method` | `const "POST"` | covered method (fail-closed) |
| `route` | `const "/v1/ingest"` | covered route; an unknown route value fails closed exactly as an unknown major does (Section 1.1) |
| `content_type` | string, `^multipart/related; boundary=[0-9A-Za-z'()+_,.:=?-]{1,70}$`, ≤ 100 chars | the complete request Content-Type, boundary included |
| `request_content_digest` | `sha256-hex` | SHA-256 over the whole multipart body as transmitted |
| `envelope_digest` | `sha256-hex` | SHA-256 over the canonical envelope bytes of part one |
| `payload_canonical_digest` | `sha256-hex` | MUST equal the envelope's `blob_digest` (STO-001) |
| `payload_transport_digest` | `sha256-hex` | MUST equal the envelope's `incoming_checksum` (PI-02) |
| `uploader_key_id` | `key-id` (SHA-256 of the encoded public key, `sha256-hex`) | the linked uploader key this attempt authorizes under |
| `authorization_epoch` | integer, 1 … 2⁶³−1 | epoch of the uploader key; rotations and revocations bump it (ID-006) |
| `authorization_timestamp` | `rfc3339-utc-timestamp` | fresh UTC timestamp bound into this attempt |
| `signature_algorithm` | `ed25519` (closed enum) | pinned; not itself covered — the linked-key record and the closed v1 enum carry it |
| `signature` | `ed25519-signature-hex` (128 lowercase hex) | the signature value; not covered |

Rules:

- **Construction (plan Section 7.2)** — the signature is Ed25519 over the
  `ingest-attempt-v1` domain label followed by one `0x00` byte, then each
  covered field as an 8-byte unsigned big-endian length plus exactly that
  many field bytes, in the pinned order
  `http_method, route, content_type, request_content_digest,
  envelope_digest, payload_canonical_digest, payload_transport_digest,
  uploader_key_id, authorization_epoch, authorization_timestamp`, with kinds
  `text, text, text, digest, digest, digest, digest, digest, u63, text`
  ([`ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json);
  golden vectors in the conformance corpus `signing.attempt_input_hex`).
- **Freshness (plan Sections 5 and 7.2; ID-007)** — the authorization window
  is 300 seconds with at most 300 seconds of clock-skew allowance (pinned as
  `authorizationWindowSeconds` / `clockSkewAllowanceSeconds` and
  cross-registered in
  [`control-envelope.json`](../../schemas/v1/control-envelope.json)). A stale
  or altered proof is rejected `auth.authorization_rejected` (HTTP 401);
  corpus proof `invalid-stale-authorization`. A stale epoch is rejected the
  same way (ID-006, ID-007).
- **Retry semantics (plan Section 7.2; ID-007, STO-004)** — none of these
  values enter the envelope. A retry after the window re-authorizes: fresh
  `authorization_timestamp` and fresh signature over the *identical* frozen
  envelope and body bytes, so occurrence and attestation identity are
  unchanged and the commit converges on the same objects. Corpus proof
  `valid-retry-after-window` (epoch 1 → 2, `already_present` × 3).
- **Authorization scope (ID-005)** — the uploader MUST be authorized for the
  declared tenant and origin client; otherwise `auth.forbidden` (HTTP 403).
  Corpus proof `invalid-cross-tenant-forbidden`. A revoked key is
  `auth.revoked` (HTTP 401, ID-006).
- **Substitution (IA-02)** — because method, route, content type, the whole
  body, the canonical envelope, and both payload digests are covered,
  transplanting a valid authorization onto altered content fails the
  signature or the digest equalities above.

### 1.4 Canonical envelope form

The envelope part is JSON in the protocol's canonical form (plan Sections
7.2–7.3):

- **Canonicalization is RFC 8785** over the protocol's value domain: ASCII
  member names, integers, strings, arrays, booleans, and `null` — no floats
  (plan Section 7.1; the `u63` discipline below). String escaping uses the
  short forms plus literal UTF-8; member order is insignificant in
  transmission.
- **Size bound (VAL-002 adjacent cap, plan Section 7.2)** — at most 65,536
  *canonical* bytes (`canonicalMaxBytes` in
  [`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)). Exceeding
  it is `envelope.size_exceeded` (HTTP 400), distinct from any payload limit.
- **Identity binds the canonical form** — `envelope_digest` is computed over
  the RFC 8785 canonicalization of the envelope, not over the transmitted
  bytes; derived identifiers likewise hash each input by its canonical wire
  text ([`ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json);
  Section 2). A transmitted part one that is reordered or differently
  whitespace is valid provided it canonicalizes: corpus proof
  `valid-reordered-envelope-framing` (identities unchanged) and
  `canonicalization.json` case `reordered-whitespace-equivalence`.
- **Malformed for the protocol (VAL-002)** — values with no RFC 8785
  canonicalization are rejected `envelope.malformed` (HTTP 400): duplicate
  member names (parsers disagree on the value) and lone surrogates (no valid
  UTF-8). A float in an integer field canonicalizes but fails the schema:
  `envelope.schema_invalid` (HTTP 400). Corpus proofs in
  `canonicalization.json` → `rejections`.
- **No normalization of identifiers (plan Section 7.4)** — opaque UTF-8
  identifiers are never case-folded, Unicode-normalized, or trimmed; NFC and
  NFD lookalikes are distinct sessions with distinct digests
  (`canonicalization.json` case `nfc-nfd-lookalikes`).

### 1.5 Envelope fields: canonical and excluded

The version 1 envelope (plan Section 7.3;
[`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)) defines 28
required and 5 optional fields. Shared shapes, byte-for-byte from
[`common.json`](../../schemas/v1/common.json):

| Shape | Bound |
|---|---|
| `uuid-v4` | `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, ≤ 36 chars, lowercase canonical text |
| `uuid-v7` | `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`, ≤ 36 chars, lowercase canonical text |
| `sha256-hex` | `^[0-9a-f]{64}$`, ≤ 64 chars, lowercase |
| `short-token` | `^[a-z0-9][a-z0-9._-]{0,63}$`, ≤ 64 chars |
| `version-token` | `^[0-9A-Za-z._+-]{1,32}$`, ≤ 32 chars |
| `opaque-id` | UTF-8, 1–1024 **bytes** (`byteMaxLength` is normative; the codepoint `maxLength` of 1024 is its superset) |
| `rfc3339-utc-timestamp` | `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}(\.[0-9]{1,9})?Z$`, ≤ 35 chars |
| `u63` | integer, 0 … 2⁶³−1 |

Required fields, grouped by role (each is `required` in the schema; all
bounds above are exact):

| Field | Shape | Role and citation |
|---|---|---|
| `protocol_version` | `const 1` | route family major; fail-closed (VAL-001) |
| `envelope_version` | `const 1` | envelope schema major; fail-closed (VAL-001) |
| `tenant_id` | `uuid-v4` | issuer-created tenant (plan 7.4) |
| `origin_client_id` | `uuid-v4` | installation that captured the source; scopes the session namespace (SID-001, SID-002) |
| `uploader_client_id` | `uuid-v4` | installation presenting this request; MAY differ from origin under relay (ID-005) |
| `harness` | `short-token` | harness identifier (plan 7.4) |
| `upstream_session_id` | `opaque-id` | the harness's own session ID, or the adapter-minted stand-in when `id_source` is `synthetic` |
| `id_source` | `upstream` \| `synthetic` | origin of the session identifier; a synthetic ID is never inferred from a path name (plan 7.4) |
| `artifact_kind` | `file-slice` \| `database-projection` | kind of source artifact (SID-004); identity-bearing |
| `adapter_id` | `short-token` | projecting adapter; input to the artifact hash (plan 7.4) |
| `adapter_projection_version` | `version-token` | projection version, preserved in provenance (plan 7.1) |
| `adapter_artifact_id` | `opaque-id` | the adapter's opaque artifact identifier (plan 7.4) |
| `generation` | `uuid-v7` | source generation of this snapshot; replacement or incompatible rewrite starts a fresh one (SID-003) |
| `range_kind` | `byte` \| `event` | coordinate kind of the range (SID-004); identity-bearing |
| `range_start` | `u63` | inclusive start coordinate; `range_start ≤ range_end` is server-side (VAL-002) |
| `range_end` | `u63` | inclusive end coordinate; ranges sit inside occurrence identity (SID-005, PI-05) |
| `blob_digest` | `sha256-hex` | SHA-256 of the canonical uncompressed payload — the one digest that names a blob (STO-001); recomputed while streaming (VAL-004) |
| `incoming_checksum` | `sha256-hex` | checksum of the payload as transported; secondary integrity, never content identity (PI-02) |
| `incoming_checksum_algorithm` | `sha256` | closed enum (fail-closed) |
| `storage_profile` | `zstd-v1` | named canonical storage encoder the server must produce (plan 7.6); closed enum (fail-closed) |
| `transport_encoding` | `identity` \| `zstd` | wire encoding of part two; the server decodes exactly one declared encoding — a misdeclaration makes the canonical bytes diverge and the request fails (PI-01) |
| `compressed_size` | `u63` | size as transported; equals `uncompressed_size` under `identity` |
| `uncompressed_size` | `u63` | size of the canonical uncompressed payload; enforced against the decoder's output (VAL-003, PI-03) |
| `capture_time` | `rfc3339-utc-timestamp` | UTC time the client captured this chunk (plan 7.3); uploader-asserted (PI-07) |
| `envelope_creation_time` | `rfc3339-utc-timestamp` | UTC time the client froze this envelope; frozen with the spool entry and reused verbatim on every retry (plan 7.3) |
| `occurrence_id` | `sha256-hex` | deterministic occurrence identity; the server re-derives and refuses a mismatch (SID-005) |
| `attestation_id` | `sha256-hex` | deterministic upload-attestation identity (STO-013) |
| `request_id` | `uuid-v7` | frozen request identifier, generated at spool creation, reused across retries, bound into envelope, attestation, receipt, and error bodies (ERR-025); a correlation handle, not a security identity |

Optional fields (absent, never `null`, when not applicable; additive within
v1 per Section 1.1):

| Field | Shape | Role |
|---|---|---|
| `source_time` | `rfc3339-utc-timestamp` | UTC timestamp embedded in or derived from the source, when one exists (plan 7.5); uploader-asserted (PI-07) |
| `parent_session_id` | `opaque-id` | upstream parent-session correlation, same harness (plan 7.3); never an identity input |
| `orchestrator_attempt_id` | `opaque-id` | orchestrator attempt correlation; joined exactly, never inferred (EC-13) |
| `trace_id` | `opaque-id` | provider trace correlation (CAP-008) |
| `inference_request_id` | `opaque-id` | inference-request correlation (Phase 9) |

**Excluded fields.** The envelope is frozen per request and MUST NOT contain
server commit time, per-attempt authorization material, the per-attempt
signature, or any server attempt correlation (plan Section 7.3). The schema
enforces this by rejecting these six names outright (`not` block in
[`ingest-envelope.json`](../../schemas/v1/ingest-envelope.json)):
`authorization_epoch`, `authorization_key_id`,
`authorization_timestamp`, `commit_time`, `correlation_id`, `signature` —
`envelope.schema_invalid` (HTTP 400, VAL-002); corpus proof
`invalid-reserved-field`. That exclusion is precisely what makes the retry
contract of Section 1.3 work: fresh authorization never changes occurrence or
attestation identity. Per-attempt and server material lives in the
signature-parameter record (Section 1.3) and the signed receipt (Section 5),
nowhere else.

Unknown fields with other names are retained inside the signed envelope
bytes and their semantics ignored (Section 1.1; plan Section 7.1).

**Cross-field consistency (VAL-002).** The schema pins syntax and bounds;
the server additionally validates, before committing an occurrence:
`range_start ≤ range_end` and range consistency with the declared sizes;
`compressed_size = uncompressed_size` when `transport_encoding` is
`identity`; calendar validity and bounds of every timestamp; the digest
equalities of Section 1.3; and re-derivation of `occurrence_id` and
`attestation_id` (corpus proof `invalid-occurrence-id-mismatch`). Declared
sizes are evidence, not authority — they are checked against the bytes the
decoder actually produces (VAL-003; Section 3 carries the payload-side
rules).

**Timestamps (plan Section 7.3).** Persisted timestamps are RFC 3339 UTC
(`Z` suffix only, at most nine fractional digits — the
`rfc3339-utc-timestamp` shape); local time is a display choice only.
Durations and retry budgets use a monotonic clock and never appear on the
wire as timestamps.

## 2. Identifier derivation and object layout

Every durable name in the raw archive — the three object keys and the
identities inside them — is a pure function of validated envelope fields.
This section pins those functions byte-exactly (plan Sections 7.4–7.5;
[`schemas/v1/ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json)
is the machine-readable construction registry), then the object layout the
keys address (STO-002, STO-003, STO-011).

### 2.1 Identifier inputs and their grammars

Derivations consume envelope fields whose shapes Section 1.5 pins. The
identity-bearing grammars (plan Section 7.4;
[`common.json`](../../schemas/v1/common.json)):

| Shape | Fields | Grammar |
|---|---|---|
| `uuid-v4` | `tenant_id`, `origin_client_id`, `uploader_client_id`, adapter-minted synthetic session IDs | lowercase canonical UUIDv4 text, 36 chars |
| `uuid-v7` | `generation`, `request_id` | lowercase canonical UUIDv7 text, 36 chars — frozen when the spool entry is created so every retry reproduces them |
| `short-token` | `harness`, `adapter_id` | `^[a-z0-9][a-z0-9._-]{0,63}$` — bounded, key-segment-safe |
| `version-token` | `adapter_projection_version` | `^[0-9A-Za-z._+-]{1,32}$` |
| `opaque-id` | `upstream_session_id`, `adapter_artifact_id` | opaque UTF-8, 1–1024 **bytes** — arbitrary content by design |

Rules:

- **No normalization (plan Section 7.4; PI-06)** — opaque identifiers are
  never case-folded, Unicode-normalized, or trimmed. NFC and NFD lookalikes
  of one visible session string are distinct sessions with distinct hashes
  and distinct keys: corpus proofs `derivations.json` cases
  `unicode-nfc`/`unicode-nfd` and scenario `valid-unicode-session`. UUIDs
  hash as lowercase canonical text and digests as lowercase hex
  (`normalization` metadata in [`common.json`](../../schemas/v1/common.json)).
- **Synthetic session IDs (plan Section 7.4)** — a missing harness session ID
  is replaced by an adapter-minted UUIDv4 recorded with
  `id_source: synthetic`; a synthetic ID is never inferred from a path name.
  The marker is durably recorded so a synthetic ID is never later mistaken
  for harness-issued provenance. Corpus proof `valid-synthetic-session-id`.
- **Hostname never enters identity (plan Section 7.4)** — hostnames are
  mutable provenance and never become an identity input or a key component.

### 2.2 The derivation framing

All four domain-separated derivations share one framing
([`ingest-identifiers.json`](../../schemas/v1/ingest-identifiers.json)
`labelEncoding`/`fieldEncoding`):

```text
preimage   = label_bytes || 0x00 || field_1 || … || field_n
field_i    = u64be(len(content_i)) || content_i
identifier = SHA-256(preimage), rendered as 64 lowercase hex characters
```

- `label_bytes` is the UTF-8 encoding of the domain label, followed by
  exactly one `0x00` byte.
- **Every** field — whatever its kind — is prefixed by its content length as
  an 8-byte unsigned big-endian integer; the length is over the content
  bytes only.
- Content by kind:

| Kind | Content bytes |
|---|---|
| `text` | UTF-8 bytes of the canonical wire text — identifiers hash as text, never as decoded binary: a UUID contributes its 36-byte lowercase text, an enum its token text |
| `digest` | the 32 raw bytes its 64-character lowercase hex name denotes (length prefix is therefore always `0x…0020`) |
| `u63` | the 8-byte unsigned big-endian rendering of the integer (length prefix is always `0x…0008`) |
| `bytes` | the raw bytes themselves — the canonical payload only, in the one label-less construction below |

The derivations, fields in pinned order:

| Value | Label | Fields (kinds, in order) |
|---|---|---|
| `session_hash` | `session-v1` | `tenant_id` (text), `origin_client_id` (text), `harness` (text), `upstream_session_id` (text) |
| `artifact_hash` | `artifact-v1` | `session_hash` (digest), `artifact_kind` (text), `adapter_id` (text), `adapter_projection_version` (text), `adapter_artifact_id` (text) |
| `occurrence_id` | `occurrence-v1` | `session_hash` (digest), `artifact_hash` (digest), `generation` (text), `range_kind` (text), `range_start` (u63), `range_end` (u63), `blob_digest` (digest) |
| `attestation_id` | `attestation-v1` | `occurrence_id` (digest), `uploader_client_id` (text), `request_id` (text) |
| `blob_digest` | *(none)* | plain SHA-256 over the canonical uncompressed payload bytes — no label, no length framing (plan Section 7.4; STO-001) |

Worked example — `session_hash` of corpus case `ascii-baseline`, whose full
pre-image hex is pinned at `derivations.json` → `preimages.session_hash`:

```text
"session-v1" as UTF-8 || 0x00
0x0000000000000024 || "0f1e2d3c-4b5a-4978-8a9b-0c1d2e3f4a5b"  (tenant, 36)
0x0000000000000024 || "11111111-2222-4333-8444-555555555555"  (origin, 36)
0x000000000000000b || "claude-code"                            (harness, 11)
0x0000000000000024 || "4f9c2f1e-8a3d-4b67-9c2f-1e8a3d4b679c"  (upstream, 36)
SHA-256 → b1be7353c6aae5eb945802a690ab0269120bcb292599d849bcb7e298867755a0
```

Rules:

- **Why this shape (plan Section 7.4)** — domain labels and length-prefixed
  opaque bytes prevent delimiter, path, case, and Unicode ambiguity: no
  field tuple can be reshaped into another's pre-image, and a deliberate
  collision requires breaking SHA-256 (PI-06).
- **`blob_digest` is the one digest that names a blob (STO-001)** — SHA-256
  of the canonical uncompressed bytes (Section 3.1), recomputed by the
  server while streaming the decoded payload (VAL-004). The envelope's
  `incoming_checksum` names the *transported* bytes and is secondary
  integrity, never content identity (PI-02).
- **The server re-derives and refuses mismatch** — `occurrence_id` and
  `attestation_id` declared in the envelope are re-derived from the
  envelope's own inputs before commit (Section 1.5 cross-field checks,
  VAL-002); corpus proof `invalid-occurrence-id-mismatch`.
- Golden pre-images for `session_hash`, `artifact_hash`, `occurrence_id`,
  `attestation_id`, and the `ingest-attempt-v1` signature input are pinned
  in `derivations.json` → `preimages`, so an implementation can test its
  framing before its hashing.

### 2.3 Collision, namespace, and conflict rules

- **Session namespace (SID-001)** — a logical session is namespaced by
  tenant, origin client, harness, and upstream session ID. Session UUID
  entropy alone is never global uniqueness (SID-002): a cloned harness UUID
  under a second origin client derives a distinct `session_hash` (EC-03).
  Corpus proof `valid-cross-tenant-second` (identical inputs under tenant
  two: distinct namespace, shared blob digest).
- **Artifact identity (plan Section 7.4)** — `artifact_hash` folds in the
  adapter and projection version, so an adapter change is a different
  artifact, never a silent rewrite. `generation` (UUIDv7) separates source
  replacement, truncation, rewind, or incompatible rewrite into a fresh
  generation under the same artifact hash — both histories are preserved
  (SID-003; EC-02).
- **Range inside occurrence identity (SID-004, SID-005; PI-05)** — because
  `range_kind`, `range_start`, `range_end`, and `blob_digest` are
  occurrence-hash inputs, overlapping, gapped, split, or re-declared ranges
  produce *distinct* deterministic occurrences: a fabricated chunk can never
  overwrite, alias, or merge with an existing one, and a genuine re-upload
  of the same range converges on the same key (STO-004).
- **Uploader and request never enter occurrence identity (plan Section 7.4;
  STO-004)** — the origin and an authorized relay presenting the same frozen
  source converge on one blob and one occurrence while recording distinct
  attestations (EC-05A; SID-006). Corpus proofs `valid-relay-upload` and
  `derivations.json` case `ascii-baseline-relay-pair` (only the attestation
  axis moves).
- **Attestation identity (STO-013)** — `attestation_id` folds in
  `uploader_client_id` and the frozen `request_id`: retries of one frozen
  request reproduce the identical attestation object (STO-004), while a
  distinct authorized uploader or a re-frozen request yields a distinct
  identity and a second, coexisting record — never an overwrite.
- **`integrity_conflict` (plan Section 7.4; EC-06; VAL-005)** — an existing
  object at a derived key whose canonical content differs or whose identity
  metadata is incompatible, when found by read-capable ingest or audit, is
  `storage.integrity_conflict` (HTTP 409) before a receipt; after a receipt
  it blocks the affected source/prefix and requires operator action. It is
  never retried as transient and never silently overwritten. Corpus proof
  `invalid-integrity-conflict`.

### 2.4 Object keys

The server derives every target key from validated fields (ID-008): a
client never selects an object key or receives arbitrary bucket write
access, and tenant authorization is enforced before any tenant-scoped key
is derived or written (SEC-003). Key segments are validated opaque IDs or
hashes only — source paths and hostnames never become key components (plan
Section 7.5; PI-06). Because every segment is a grammar-checked value
(Section 2.1) or a hex digest, assembly is deterministic and tenant-scoped
(STO-003): identical validated inputs produce the identical key on any
server or replica — with the identity rules above, this is what makes a
retry after a lost response converge on the same objects instead of
duplicating them (STO-004).

Assembly recipes, segment by segment (patterns pinned in
[`common.json`](../../schemas/v1/common.json) as
`blob-object-key`/`occurrence-object-key`/`attestation-object-key`, each at
most 512 characters):

| Namespace | Key |
|---|---|
| blob | `tenants/<tenant_id>/v1/raw/blobs/zstd-v1/sha256/<first 2 hex of blob_digest>/<blob_digest>.zst` |
| occurrence manifest | `tenants/<tenant_id>/v1/raw/occurrences/<origin_client_id>/<harness>/<first 2 hex of session_hash>/<session_hash>/<occurrence_id>.json` |
| upload attestation | `tenants/<tenant_id>/v1/raw/attestations/<first 2 hex of occurrence_id>/<occurrence_id>/<attestation_id>.json` |

Rules:

- The two-hex segment is a shard — the first two characters of the
  immediately following digest — for key-space fan-out only; the full value
  always follows it, so the shard carries no meaning of its own.
- The blob key embeds the storage-profile name (`zstd-v1`): profile and
  prefix change together, never independently (plan Sections 7.5–7.6;
  Section 3.2).
- Raw upstream identifiers are hashed into keys and never embedded (plan
  Section 7.5): the original `upstream_session_id` lives only inside the
  restricted raw manifest (SEC-002), keeping keys free of source-chosen
  bytes.
- Blob keys are tenant-scoped, so identical canonical bytes under two
  tenants are two blob objects sharing one digest value; within one tenant,
  identical bytes from distinct sessions are one blob plus distinct
  occurrence manifests — deduplication working, not a conflict (STO-002;
  corpus proof `valid-cross-tenant-second`).
- Other v1 namespaces beneath `tenants/<tenant_id>/v1/` (`control/`,
  `catalog/`, `derived/`) follow plan Section 7.5; derived artifacts live
  under pipeline-versioned prefixes and retain references to raw occurrence
  IDs (STO-012). They are outside this section's scope.

### 2.5 The stored objects

One successful ingest commits three objects, in this order: the raw blob,
then the occurrence manifest, then the upload attestation — a request
succeeds only after all three are durably accepted (RCPT-001; the commit
mechanics are Section 4's scope).

**Raw blob** — the canonical payload encoded exactly as the `zstd-v1`
storage profile pins (Section 3.2), stored at the blob key with the `.zst`
suffix. Addressed by SHA-256 of its canonical *uncompressed* bytes:
compressed bytes persist beneath an uncompressed content address (STO-001;
VAL-006). One blob object per (tenant, `blob_digest`) regardless of how
many occurrences reference it (STO-002).

**Occurrence manifest**
([`occurrence-manifest.json`](../../schemas/v1/occurrence-manifest.json)) —
RFC 8785 canonical JSON (bare canonical bytes; the committed example
bundle's one trailing LF per file is a bundle convention, not part of the
object), media type `application/vnd.agent-archivist.occurrence+json;version=1`,
at the occurrence key. Nineteen required fields and one optional
(`source_time`, omitted — never `null` — when the source carries none). It
carries what STO-010 demands — blob digest, logical session identity,
source coordinates, origin, adapter/projection version, schema version —
and nothing else:

| Members | Fields |
|---|---|
| Identity inputs | `tenant_id`, `origin_client_id`, `harness`, `upstream_session_id`, `id_source`, `artifact_kind`, `adapter_id`, `adapter_projection_version`, `adapter_artifact_id`, `generation`, `range_kind`, `range_start`, `range_end` |
| Identity derivations | `session_hash`, `artifact_hash`, `occurrence_id` |
| Content binding | `blob_digest`, `storage_profile` |
| Version | `occurrence_version` (`const 1`) |
| Optional | `source_time` |

Rules:

- **Source stability (STO-010)** — every field is an identity-hash input or
  a deterministic derivation of identity inputs, so the canonical bytes
  never vary by uploader or upload attempt. Uploader, request, transport,
  per-attempt authorization, and server commit material are excluded: the
  schema rejects sixteen reserved names outright
  (`attestation_id`, `authorization_epoch`, `authorization_key_id`,
  `authorization_timestamp`, `capture_time`, `commit_time`,
  `compressed_size`, `correlation_id`, `delegation`,
  `envelope_creation_time`, `incoming_checksum`,
  `incoming_checksum_algorithm`, `request_id`, `signature`,
  `transport_encoding`, `uploader_client_id`) — the separation that keeps a
  relay from overwriting source provenance (SID-006; EC-05A).
- **One manifest per distinct `occurrence_id`** (STO-002), even when
  several occurrences reference one blob.
- **Self-verifying (STO-011)** — `session_hash`, `artifact_hash`, and
  `occurrence_id` are each re-derivable from the manifest's own fields alone
  per Section 2.2; an auditor needs nothing but the stored object, and
  re-derivation refusing a mismatch is the `integrity_conflict` rule of
  Section 2.3 (VAL-005; PI-07 containment — fabrication creates new
  attributed objects, never corrupts archived ones).
- **Rebuild sufficiency (STO-011)** — the manifest carries the full
  artifact-identity tuple and the verbatim `upstream_session_id` because
  the wire envelope is not durable: without them the artifact's identity
  would survive only as an unrecoverable hash input and catalogs could not
  be rebuilt from the raw namespaces.
- The blob's uncompressed size is recoverable from its `zstd-v1` frame
  header (Section 3.2), so no size field is duplicated here.

**Upload attestation**
([`upload-attestation.json`](../../schemas/v1/upload-attestation.json)) —
RFC 8785 canonical JSON, media type
`application/vnd.agent-archivist.attestation+json;version=1`, at the
attestation key, written after the bound occurrence manifest is durable
(RCPT-001). Ten required fields: `attestation_id`, `attestation_version`
(`const 1`), `tenant_id`, `occurrence_id`, `origin_client_id`,
`uploader_client_id`, `request_id`, `delegation`, `capture_time`,
`envelope_creation_time`. It binds exactly what STO-013 demands — the
occurrence ID, origin, uploader, frozen request ID, capture/envelope
timestamps, delegation relation, and schema version — and never duplicates
transcript content. Per-attempt authorization, the signature, and server
commit time exist only in the signed receipt (Section 5); the schema
rejects six reserved names outright (`authorization_epoch`,
`authorization_key_id`, `authorization_timestamp`, `commit_time`,
`correlation_id`, `signature`). `delegation` is a closed fail-closed enum:
`direct` requires `uploader_client_id = origin_client_id`; `relay` requires
them to differ and the uploader to hold verified origin/uploader
delegation (ID-005) — server-side validation, not schema syntax (VAL-002).

Each envelope field lands in exactly one durable home, or deliberately
nowhere (plan Section 7.5;
[raw-provenance-schemas](../notes/raw-provenance-schemas.md)):

| Envelope field | Occurrence manifest | Upload attestation |
|---|---|---|
| `tenant_id`, `origin_client_id` | yes | yes |
| `harness`, `upstream_session_id`, `id_source` | yes | — |
| `artifact_kind`, `adapter_id`, `adapter_projection_version`, `adapter_artifact_id`, `generation`, `range_kind`, `range_start`, `range_end` | yes | — |
| `blob_digest`, `storage_profile` | yes | — |
| `session_hash`, `artifact_hash`, `occurrence_id` | yes (self-verifying) | `occurrence_id` only |
| `source_time` | yes, when present | — |
| `uploader_client_id`, `request_id` | — | yes |
| `capture_time`, `envelope_creation_time` | — | yes (plus server-derived `delegation`) |
| `transport_encoding`, `incoming_checksum(_algorithm)`, `compressed_size`, `uncompressed_size` | — | — |

The wire-only rows are deliberate: transport checksums and sizes describe
one delivery attempt, not the source or the frozen request.

## 3. Canonical payload and the `zstd-v1` storage profile

### 3.1 Canonical payload bytes

What `blob_digest` names. By `artifact_kind` (plan Section 7.6; SID-004):

- **`file-slice`** — the exact, complete-record byte slice of the file
  source: the bytes the source contains across the declared range, cut only
  on complete record boundaries. An incomplete trailing record waits for a
  later pass; it is never uploaded half-cut (CAP-003).
- **`database-projection`** — one RFC 8785 JSON object plus one LF per
  projected event, emitted from a versioned field allowlist over a
  read-only source connection (CAP-004). The adapter never uploads the
  application database wholesale.

Chunk boundaries: adapters chunk on complete JSONL records, database
events/messages, immutable source objects, or provider event boundaries —
never splitting a structured record to meet the 16 MiB target chunk (plan
Section 7.6; Section 3.4). A single record over 256 MiB is quarantined
`request.record_too_large` (HTTP 413), reported as a coverage gap, and
never silently truncated (EC-07).

`blob_digest` is SHA-256 over these canonical uncompressed bytes with no
label and no framing (Section 2.2; STO-001). The server recomputes it while
streaming the decoded payload (VAL-004) and derives the blob key from the
*computed* value — the envelope's declared digest is evidence, never
authority (PI-01). Any mismatch aborts the uncommitted write before
anything lands under the claimed address (VAL-005).

### 3.2 The `zstd-v1` storage profile

`storage_profile` names the canonical storage encoder the server must
produce (Section 1.5; plan Sections 7.5–7.6). Version 1 has exactly one
profile, `zstd-v1`, pinned as (plan Section 7.6):

| Parameter | Value |
|---|---|
| Algorithm | Zstandard |
| Compression level | 3 |
| Threading | single-threaded |
| Dictionary | none |
| Frame content size | enabled — the uncompressed length travels in the frame header |
| Frame checksum | enabled — stored-frame integrity |
| Encoder dependency | pinned for the lifetime of the profile |

Rules:

- **Server-owned encoding (VAL-006)** — compression MUST have a
  deterministic canonical form when its bytes persist beneath an
  uncompressed content address, and that form is server-produced: the
  server decodes the declared transport (Section 3.3) and itself encodes
  the stored frame. Client-chosen compression output is never persisted —
  plan Section 7.6 rejects client-specific gzip/zstd output under one key
  precisely because it varies by implementation. Identical canonical bytes
  therefore produce identical stored bytes on any platform, server, or
  retry.
- **Address versus representation (STO-001; PI-02)** — the key names
  SHA-256 of the canonical uncompressed bytes; the stored bytes are the
  `zstd-v1` frame of them. The only basis for content identity is:
  decompress → SHA-256 the uncompressed stream → compare against the
  address. The frame's embedded content size and checksum are integrity of
  the stored object — and an implementation MAY additionally verify a
  backend-native checksum of stored bytes (STO-001) — but none of these is
  ever promoted to content identity, nor is the transport checksum or
  either declared size (PI-02).
- **Size recoverability** — the enabled content size places the
  uncompressed length in the frame header, which is why no manifest field
  duplicates it (Section 2.5) and why the read path can bound its
  allocation before decompressing.
- **Profile immutability** — these parameters are frozen for the life of
  the profile. A replacement encoder (the plan Section 7.6 revisit
  triggers: a correctness/security defect, median compression below 1.2:1,
  or sustained reference-runner throughput below 50 MiB/s) is a *new named
  profile under a new key prefix*, never a rewrite of what `zstd-v1` means
  (plan Sections 7.5–7.6). `storage_profile` is a closed fail-closed enum
  (Section 1.1) and appears in the blob key prefix, so profile and prefix
  move together.
- **Write path** — canonical bytes stream through the pinned encoder into
  uncommitted multipart parts under bounded memory; the upload completes
  only after all sizes, digests, and the request signature verify, and
  uncommitted parts are aborted on any failure (VAL-008; plan Section 7.7 —
  the commit contract itself is Section 4's scope).

### 3.3 Transport decoding is not storage encoding

`transport_encoding` (`identity` | `zstd`) declares the wire form of
request part two (Section 1.2); the `zstd-v1` profile governs the stored
form. The two never collapse (plan Section 7.6; PI-01):

- The server decodes **exactly one** declared encoding per request. A
  misdeclaration makes the decoded canonical bytes diverge, the recomputed
  `blob_digest` mismatch, and the request fail — aborting the uncommitted
  write (VAL-005; PI-01).
- `identity` carries the canonical bytes unchanged; `compressed_size` MUST
  equal `uncompressed_size` (VAL-002 cross-field check, Section 1.5).
- `zstd` carries one Zstandard frame of the canonical bytes at any legal
  level — a transport convenience only. Transport bytes are never
  persisted: the server hashes the decoded canonical bytes and re-encodes
  them itself per Section 3.2.
- The v1 conformance corpus pins `identity` vectors only, deliberately: a
  golden zstd transport digest would pin one compressor build and stop
  being language-neutral
  ([corpus conventions](../notes/conformance-corpus.md)); adding `zstd`
  transport vectors requires the build-independent frame pin decided there
  first.

### 3.4 Limits

Defaults and hard caps (plan Section 7.6; VAL-003):

| Limit | Version 1 value |
|---|---:|
| Target canonical chunk | 16 MiB |
| Single structured record | 256 MiB maximum |
| Envelope | 64 KiB maximum (Section 1.4) |
| Expansion ratio | 100:1 maximum |
| Request duration | 15 minutes maximum |
| Multipart part | 8 MiB |
| In-flight uploads | 16 per server process |
| In-flight uploads per client | 4 per server process |
| New request rate | 60/minute/client/replica, burst 8 |

Rules:

- Ceilings are enforced against the bytes the decoder actually produces,
  not the declared values — a lying declaration buys nothing once the
  stream overruns (VAL-003; PI-03).
- Oversized-but-splittable payloads are `request.payload_too_large`
  (HTTP 413, rechunk at a record boundary and resubmit); a ratio overrun is
  `request.expansion_ratio_exceeded` (413); an unsplittable record over
  256 MiB is `request.record_too_large` (413, quarantine and report the
  coverage gap); the duration cap surfaces as `request.deadline_exceeded`
  (408) — all registered in [`tools/error-codes.toml`](../../tools/error-codes.toml).
- Limits may be lowered by policy; raising a hard cap requires the
  resource/fuzz suite on the same commit (plan Section 7.6).

### 3.5 How this section is verified

- **Cross-platform golden blobs** — the same canonical bytes must compress
  to identical stored bytes on every platform (plan Section 7.6
  enforced-by; Phase 2 storage core).
- **Decompression fuzzing and limit-boundary tests** enforce the Section
  3.4 ceilings against decoder output; the Phase 4 fuzz gate requires that
  fuzzed envelopes and compressed streams not panic, over-allocate, or
  commit invalid objects (plan Sections 7.6 and 10; PI-03).
- The identity-transport and derivation sides are pinned today by the
  conformance and provenance bundles (Sections 2.6 and 3.3).
- The storage compatibility suite (plan Section 10) exercises read-side
  decompress-and-verify against the canonical address on the reference S3
  implementations.
